# sloverb

Slowed and reverb or nightcore for any song, in the browser. Vite + React + TypeScript and plain Web Audio. Songs are played, changed and saved on the listener's device. The one exception is YouTube links, which are downloaded by a worker on Umair's always-on Windows PC at home and handed back to the browser through a small relay on Render.

Live at https://sloverb.app. Two rules below apply to every change you make: keep the documentation true, and keep it fast. Read this file, then `docs/decisions.md`, then `README.md`, then `docs/accessibility.md` if the task touches anything on screen or how it is used, `docs/youtube-import.md` and `docs/worker.md` if it touches imports, `docs/analytics.md` if it touches what is recorded about them, and `docs/seo.md` if it touches the `<head>` of `index.html`, anything in `public/`, or the words that describe sloverb to search engines and link previews.

## Keeping the documentation true

This rule applies to every change, by any agent or person, for as long as the project exists. The documentation is how the next agent understands sloverb, so a change isn't finished until the docs say what is now true.

- **In the same commit as the change**, update whichever of these it affects:
  - `CLAUDE.md` for rules, hosting, commands, known gaps, and anything an agent must know before touching the code.
  - `README.md` for what sloverb does, how to run it, and which file does what.
  - `docs/*.md` for the detail of a part (imports, the Windows worker, anything new that deserves its own page).
  - `docs/decisions.md` when something is decided, or an earlier decision is changed or reversed.
  - `docs/changelog.md`, one dated line for anything a visitor, Umair or a future agent would notice.
- **Fix what's wrong when you find it.** If something in the docs no longer matches the code or the live site, correct it, even when it isn't part of your task.
- **Write it so a new agent with no memory of this conversation can act on it.** Say why, not only what. Use dates, not "today". Name files, services and settings exactly.
- **Delete what stops being true** rather than piling up exceptions. A gap that gets fixed comes off Known gaps and goes into the changelog.
- **CI enforces this.** The `docs` job in `.github/workflows/ci.yml` fails when a push or PR changes code or config without touching `CLAUDE.md`, `README.md` or `docs/`. Only when nothing a future agent needs to know has changed (a typo, a tweak to a number already described, a refactor that leaves behaviour and structure alone), put `[no-docs: reason]` in the commit message or PR title. A failing check also holds back the Render deploy, which waits for checks to pass.
- **Decisions can change.** Nothing in these docs is permanent because it was written down. A future agent may change a rule, the hosting, the design or anything else once it understands why the current choice was made (see `docs/decisions.md`) and Umair agrees where the change is his call. Record the new decision there, mark the old one as replaced and say why, and update every other doc it touches. The exceptions are the things Umair said must be kept: the `original` branch and `v1-original` tag, keeping it fast, and the style section below.
- Everything lives in this repo and on GitHub, never only in an agent's private memory or a chat.
- `AGENTS.md` points other tools here, and `.github/pull_request_template.md` carries the same checklist into every PR.


## Keeping it fast

This rule applies to every change, by any agent or person, for as long as the project exists, exactly like keeping the documentation true. Umair wants sloverb to feel lightning fast: every tap, hover, drag and screen change has to answer instantly, on any phone, old and cheap ones included. On 2026-11-12 he found it had become lazy after a run of visual additions, and every effect was reworked to keep its look and lose its cost (D14 in `docs/decisions.md`). Don't let it drift back.

- **Before you call any change finished**, ask whether it makes anything slower to answer, heavier to draw, or slower to load, and check it in a browser if it touches what is on screen. A change that looks good and feels slow is not done.
- **`npm test` runs `scripts/check-speed.mjs` first**, and so does the `check` job in CI, so a push that breaks one of the rules a machine can see fails before it deploys. It flags transitions or one-off animations over 0.25s, animating properties that repaint or relayout (`height`, `width`, `box-shadow`, `background-position` and so on), transitions on properties that repaint, `backdrop-filter`, and styles set on the whole page from script. A line that genuinely needs an exception says why on the same line with a comment containing `speed-ok:`. Don't add one to get a change through, fix the change.
- **The check can't see everything.** These rules are on you:
  - Anything a person touches answers a press in `--press` (0.04s) and a hover or release in `--quick` (0.12s), both in `src/styles.css`. Nothing they touch takes longer than about 0.2s, screen changes included.
  - Never set a value that changes every frame on `:root` or `body`, every element would restyle every frame. The music level (`--level`) goes only to elements with the class `hears`. The look is the one thing set on the whole page, as the attributes `data-theme`, `data-glow` and `data-still` (the glow effect at `off`) on `<html>`, and only at the moment someone picks one.
  - Never animate `box-shadow`, `height`, `width`, `filter` sizes or `background-position` every frame. Draw a thing once on its own layer and fade its `opacity`, or move it with `transform` (see `.rest` and `.now-playing__bars`). The lights behind the page (`.aura i`) follow the same rule however a glow is shaped: each is drawn once, and only its `transform`, `translate`, `scale` and `opacity` change.
  - No `backdrop-filter` anywhere. Over the moving light behind the page it re-blurs every frame, and the last two uses, on the toast and the drop overlay, were taken out on 2026-11-27 (D33).
  - Prefer loops the browser runs (CSS animations, Web Animations) over `requestAnimationFrame`. The light (`Aura`) and the waveform are the two script loops, and the engine listens once per frame for both (`listen` in `src/audio/engine.ts`, behind `level()` and `hear()`).
  - Play starts at once when the press is a real tap (`navigator.userActivation`), instead of waiting for the sound hardware to wake.
  - iPhones only show `:active` on a page that listens for touches, which is the empty `touchstart` listener in `src/main.tsx`. Don't remove it.
  - Files under `/assets/` have hashed names and are cached for a year (`vercel.json`), so a return visit loads from the phone.
  - Don't add a dependency or a big file to the page for an effect. React is most of the JavaScript already.
  - Anything new that moves with the music goes through `hears` and must not restyle, relayout or repaint the page each frame.

## How it fits together

```
browser at sloverb.app (Vercel)
  │  local files: decoded, played and saved on the device, never uploaded
  │  youtube link:
  ▼
https://api.sloverb.app   Render web service "sloverb-import" (free plan, relay mode)
  ▲  holds jobs in memory for 10 minutes, no database, no disk that survives a restart
  │  outbound, signed HTTPS only (claim job, report progress, upload MP3)
  │
worker on Umair's Windows PC   scheduled task "Sloverb Worker", started at boot before login
     yt-dlp + FFmpeg turn one video into an MP3
     keeps a journal of what visitors asked for, in analytics\ beside its key, never anywhere else
```

- YouTube refuses downloads from Render's addresses (both regions tried), which is why the download happens at home. Nobody ever connects to the PC. It only makes outgoing requests. Until 2026-11-16 it was Umair's Mac (D23), and `macos/` can still put it back there.
- The browser talks to `api.sloverb.app`, never to `sloverb-import.onrender.com`. Ad blockers block `onrender.com` when it is called from sloverb.app (Chrome shows `net::ERR_BLOCKED_BY_CLIENT`), so the API must stay on a sloverb.app subdomain. The worker still uses the `onrender.com` address, which is fine because no browser is involved.
- Imports only work while the PC is on, online and not paused. It is always on, and the worker comes back by itself after a restart, no login needed. Otherwise `/healthz` says `"available": false` and the site shows `imports are offline, try later`.
- An imported MP3 goes into `engine.add([{ file, name }])` like any other file, so the queue, effects and save are the same for both.
- Since 2026-11-27 the relay notes each visitor's request to it (address, country, browser, the video, how it ended) in memory and nowhere else, and the worker collects those notes over the same signed channel and keeps them on the PC, where Umair can watch them live (`docs/analytics.md`, D28). It only ever sees YouTube imports. A song opened from a device still never leaves it.
- Since 2026-11-27 the site also loads Vercel Web Analytics (`/_vercel/insights/script.js`, from the inline script in the head of `index.html`, D32), which counts page views without cookies and shows them only in the project's Analytics tab on Vercel. It sends nothing about songs. It only counts once Web Analytics is enabled on the project there.

## Rules that are easy to break

- sloverb meets WCAG 2.2 AA (D25), and `docs/accessibility.md` says how, so read it before changing anything on screen. The parts most easily undone: every control keeps a name that starts with the word it shows; anything that hides or removes the control being used hands the focus on (the effect on `shown` in `src/App.tsx`, `reset`, `save` using `aria-disabled` rather than `disabled`, `LinkImport`); something that changes without the focus moving says so through `announce()` in `src/ui.tsx`, never a live region that appears with its words in it; a new slider-like control takes the arrows, Page Up and Page Down, Home and End; and a Web Animation must check `calm()` itself, because the stylesheet's rule for reduced motion can't stop one. Words only a screen reader hears (`.unseen`) follow the same style as the words on screen: lowercase, plain, short.
- A change of screen never waits on the browser. `closePage` and `closeAdding` in `src/App.tsx` change what is on screen at once and tidy the history afterwards (`history.back()`, then a check 400ms later that clears the address by hand if the browser didn't go back), and the effect that moves `shown` to `view` falls back to a plain switch if the View Transition hasn't run its callback within 250ms or throws. Before 2026-11-12 both waited: closing called `history.back()` and relied on `popstate`, and the screen only changed inside the transition's callback. On Umair's iPhone, after opening the LinkedIn link in a new tab and coming back, `back` on `info` then did nothing however often it was pressed. Which of the two Safari failed at was never established (it could not be reproduced off the phone), so both are guarded. Keep it that way: anything a person presses must do its job even if the nicety round it fails.
- The live player and a save both go through `chain()` in `src/audio/chain.ts`, so the file is what was playing. Never add something to one and not the other.
- `src/core` has no browser APIs in it, which is why it can be tested in node. Sums go in `core`, Web Audio goes in `audio`.
- The look is kept in `localStorage` under `sloverb.look` as `{ theme, glow, amount }`: the theme (`dark` or `light`), the name of the glow, and how much of it moves with the music from 0 to 1. Three places read that name or those lists and must agree: `src/look.ts`, the small script in `index.html` that puts a kept look's `data-theme` and `data-glow` on the page before the first paint, over the default written on the `<html>` tag, so a light page never opens black (and `data-still` when the amount is 0, so a page that was stilled doesn't start moving), and `THEMES` and `GLOWS` in `src/core/look.ts`. Nothing kept, or anything unreadable, gets the default, `light` with `rose` and all of it (`readLook`), and storage being blocked only means the look isn't remembered. A look is only ever kept once someone changes something on `themes`, so the default reaches everyone who never has. Until 2026-11-14 it was `{ theme, glow }` with six themes and `glow` as the amount, and devices still hold that: `readLook` turns `default` and the short-lived `dark` into `dark` with `classic`, `minimal` into `mono`, `ember`, `ocean` and `forest` into the glow of the same name on `dark`, the old `light` into `light` with `classic`, and a number under `glow` into the amount. Those devices chose what they have while dark was what everyone got, so they keep it now that the default is light: a kept theme name is never replaced by the default, only a missing or unknown one is (`NAMED` in `src/core/look.ts`). Keep that reading, and its tests, for as long as old devices might come back.
- The room is seeded and comes out the same every time. Tests rely on that.
- A sample under the knee passes through `hold()` untouched, so `original` with no reverb is the song as it was, 1 dB quieter. Keep it that way.
- No song files in the repo, and no demo song. `public/local/` is ignored by git, for trying real songs.
- Only the song that is playing is held decoded. The rest of the list waits as files and is decoded when its turn comes, so a long list doesn't run a phone out of memory. Don't cache decoded songs.
- A song's speed and reverb live on its `Track`, and the engine's `state` only mirrors the one that is playing. Anything that changes them goes through `apply()` in `src/audio/engine.ts`, which writes both, and `load()` puts a song's own settings on before it starts. A `reset` still gliding when the song changes is finished for the song it belonged to rather than carried into the next.
- Songs come in through `engine.add([{ file, name }])` and nowhere else, YouTube imports included. With nothing open the first of them plays; with a song open or opening they go on the end of the list and whatever is playing carries on, with a short `added` note. Adding never interrupts the song that is playing.
- Keep the browser's API address on a sloverb.app subdomain (see above). If it ever has to change, the order is: Render custom domain, DNS record, wait for Render to show the certificate, then the Vercel variable, then redeploy.
- The relay and the worker are deployed at different times (Render on push, the PC only when someone reruns the installer). Keep the job protocol (`"version": 1`) backward compatible, or bump it on both sides together.
- One Uvicorn process on Render, never more. Jobs, rate limits and the replay guard live in that process's memory.
- Never put a secret in a `VITE_` variable, it ends up in the public JavaScript. The worker's private key never leaves the PC, Render only has the public key.
- `backend/worker.py` and `backend/app.py` run on Windows and on macOS. Anything that starts or kills processes, locks files, reads the battery or holds off sleep needs both ways (`WINDOWS` in `backend/worker.py`, `backend/winjob.py`). `backend/tests/test_windows.py` runs in the `windows` CI job.
- YouTube links are checked twice, in the browser (`src/core/youtube.ts`) and again on the server and the worker (`backend/urls.py`). Change both together.
- Search engines and link previews read words of their own: the description (twice, `description` and `og:description`), the structured data at the foot of `index.html`, and the `<noscript>` page, which is `info`'s sentence. Keep them true when a feature changes, keep them in the style of `info`, never put words for search where a visitor can't see them, and never aim sloverb at YouTube downloading. `docs/seo.md` says why for each.
- Error messages a visitor can see are a fixed list (`safe_errors` in `backend/relay.py`, and the `ValueError`s in `backend/extract.py`). yt-dlp's own errors can contain signed URLs and addresses, so never pass them through. Since 2026-11-27 they are kept, as `detail` on the job, for the journal on the machine that ran the download and for nothing else: never in `public()`, never in what the worker sends the relay.
- A download that fails in a way that may not happen twice is run again, up to three goes in all, each in a fresh process and all inside the one four-minute deadline (`attempts` in `backend/app.py`, D29). Umair found on 2026-11-27 that a link could come back `youtube blocked this import` and download when pasted again straight away. Which failures are worth another go is decided in one place, `verdict` in `backend/extract.py`: a refusal and anything unexplained are, a video that is private, gone, age-checked or turned away by our own limits is not. Keep that honest when adding a message, a wrong `again` either hammers YouTube for nothing or brings the bug back. The cause at YouTube's end is still not known (Known gaps).
- The journal (`docs/analytics.md`) has rules of its own. `backend/tests/test_analytics.py` holds the ones a test can:
  - A job's id never goes in an event, only `tag()` of it (`backend/events.py`). The id is all it takes to read or cancel a job.
  - What a visitor typed is only recorded once it has turned out to be a YouTube video link.
  - Render keeps nothing. Events wait in memory for the worker, capped in number and in pace (`Events`), and Uvicorn's access log stays off. Don't add a file, a database or a `print` of a request there.
  - Noting a request must never be what fails it, and the journal must never be what stops an import: `notice` in `backend/app.py`, and `note` and `collect` in `backend/worker.py`, swallow their own errors on purpose.
  - Everything in an event that came from outside (headers, titles) is other people's words. It is stripped of control characters three times (`clean` on the relay, `tidy` on the worker, `line` when printed) and reaches the dashboard page only as `textContent`. Never `innerHTML` in `backend/dashboard.html`, and never print an event without `line`.
  - The dashboard listens on `127.0.0.1` only, answers only GET, and is started by hand. The worker service itself must go on listening on nothing.
  - No journal data in the repo, in an issue, in a commit message or in a doc. It is real people's addresses and the repo is public. Made-up events use the addresses kept for documentation (`203.0.113.x`, `198.51.100.x`, `192.0.2.x`).
  - The events answer carries `"version": 1` like the job protocol, and each side must go on working with an older other side.
  - On Windows the journal's folder takes its permissions from the folder it is in and is never given a mode of its own (`Journal.keep` in `backend/analytics.py`). Python makes of `0o700` there a folder open only to its owner, SYSTEM and administrators, and what the boot task creates is owned by the Administrators group rather than the person. So the first build installed on the PC, on 2026-11-27, wrote a journal that `watch`, `stats` and `dashboard` could not read from an ordinary terminal, and they showed nothing without saying why. Fixed the same day, and the installer's approved step repairs a folder made that way. `backend/tests/test_windows.py` holds it. The same goes for anything else the worker creates that a person has to read: the worker and the person at the keyboard are the same account but not the same owner.

## Known gaps

Found on 2026-11-10 and not fixed yet. Raise them rather than assuming they are settled.

- There is no limit on imports per address at the moment. It was 6 an hour until 2026-11-12, when Umair hit it himself while testing and asked for it not to count for now (`rate_limit = 0` in `backend/app.py`, where 0 means off). Only three imports can be in flight at once (`capacity`), which is all that stands between a busy visitor and his PC. If it comes back, know that it was easy to dodge: Uvicorn runs with `--forwarded-allow-ips='*'`, so it takes the visitor's address from the first `X-Forwarded-For` entry, which a visitor can write, and it counted failed and cancelled attempts too.
- The worker checks in every few seconds, so the free Render service never sleeps. That uses about 744 of the 750 free hours a month.
- The site only checks `status: ok` from `/healthz`, not `available`, so the YouTube box shows even when the worker is offline and the visitor finds out after pressing open.
- Render gives the worker 270 seconds per job and the worker's own download limit is 240, which leaves 30 seconds to upload.
- The Docker image still carries Node, FFmpeg and a YouTube token generator that relay mode never uses.
- Found 2026-11-26: it is not known whether sloverb is set up in Google Search Console or Bing Webmaster Tools, which only Umair can do. The steps are in `docs/seo.md`.
- From 2026-11-27, about the journal (`docs/analytics.md`):
  - Render does pass Cloudflare's `CF-IPCountry` and `CF-Ray` through to the app: the first live events on 2026-11-27 carried `country` and `edge`. One request among them, a 404 on `/`, carried neither, so not everything that reaches the relay comes by way of Cloudflare's headers. For a request like that the address is the first `X-Forwarded-For` entry, which a visitor can write (`visitor` in `backend/events.py`).
  - The `geo` command has been run on Linux but not yet on the PC.
  - Nothing checks that the worker machine's clock is kept in time, and the relay refuses the worker once it is more than 90 seconds out. The journal shows the drift: the worker's time for a job against the relay's for the same one (`job.claimed` and `import.claimed`). They were 18 seconds apart on 2026-11-27. On Windows the Windows Time service sets the clock. On a home PC it is not left running, a task of Windows' own starts it now and then, and when that fails nothing says so (it was failing on 2026-11-27), so look with `w32tm /query /status` and at the task `Time Synchronization\SynchronizeTime`.
  - Visitors aren't told that their address and what they imported are kept, and nothing is ever deleted. Both are Umair's to decide.
  - The journal only knows about YouTube imports. Songs opened from a device never reach the backend (D2).
  - `worker.log` is only moved aside when the worker starts, so on a PC that runs for months it grows past its half megabyte.
- Found 2026-11-27 and not settled: whether the worker on Windows really runs without administrator rights. The task is registered as `LeastPrivilege` (`task_xml` in `windows/install.py`) and `docs/worker.md` says not elevated, but on an administrator's account the files it creates are owned by the Administrators group and an ordinary terminal is refused when it tries to open its processes, which is how a full administrator token behaves. It matters because yt-dlp, FFmpeg and Node read what YouTube sends. It has to be looked at from an administrator terminal, which an agent can't open.
- From 2026-11-27: why YouTube refuses a download and then allows the same one a moment later is not known. Nothing recorded what yt-dlp said until that day, and YouTube can't be reached from a cloud session to try it. The retry (D29) is the second paste done for the visitor, checked against a made-up refusal and against a real extractor that was refused every time, never against a refusal that then lifted. The journal now keeps what yt-dlp said on every failed go (`job.retried` in `docs/analytics.md`), so after a few days on the PC `sloverb-worker.cmd stats` says how often it happens and `watch` or `worker.log` say why. Read those before changing anything about it.

## Checking it works

There is no way to listen from here, so measure. In development the engine is on the window as `sloverb`. From the browser console you can drive it (`sloverb.tune({ reverb: 0.7 })`, `sloverb.seek(30)`), read `sloverb.snapshot()` and `sloverb.position()`, and render through `chain()` in an `OfflineAudioContext` to read levels and peaks.

## Style

That is the theme called `light` with the glow called `rose`, and it is what every first visit gets, and anyone who has never chosen a look. Umair made it the default on 2026-11-14 (D20). The stylesheet is not one of them: what it writes first is still `dark` with `classic`, and every other look says where it differs from that. Leave it that way, reordering that block would break the rule about which of two equal rules wins.
- The look is two choices, since 2026-11-14 at Umair's request (D18): a theme, which is only `dark` or `light`, and a glow, which is the three colours of the page's light and the way that light moves behind it. Before that there were six themes and the colours came with the theme (D15).
- One set of colours per glow, always as a gradient of three in the same order left to right (`--c1` to `--c3` and `--grad` in `src/styles.css`; the waveform reads the same three through `looks.paint()` in `src/look.ts`). On `classic` they are the blue, purple and pink of the first sloverb, as light on a black page. Since 2026-11-27 (D33) the three colour only what shows the music or the sound: the waveform behind the playhead, the fills of the sliders and of the YouTube import bar, the three bars beside the playing song, and the light in the background. Never a fourth colour within a glow. Everything else is in the colour of the page's words: the wordmark, `browse files`, play and save are plain ink (`--text`, with `--ink` for what is written on them), and the lines round things are that colour let through part way (`--edge`).
- Nothing on the page glows, and keep it that way (D33). On 2026-11-27 Umair asked for anything that made sloverb look tacky or like "AI slop" to go, naming the glowing edges on the start screen. That look is, by wide agreement, a stack of the same few things: gradient text, a gradient or glowing border, a coloured `box-shadow` round cards, buttons and inputs, frosted glass, shimmer and other motion that reports nothing, and blurred blobs of colour. So: no coloured `box-shadow` and no `filter` glow on anything, no gradient as a border or inside letters, no `backdrop-filter`, no hover that grows a thing (a hover changes a colour or an opacity), and no entrance that slides. What went that day: the three-colour edge and glow round the drop box and the link box (now a dashed and a solid line in `--edge`), the gradient drifting through the wordmark, the blurred ring turning behind play, the glow under the speed slider, the reverb slider and save, the glow on every grip, the glow reverb put round the waveform, the turning ring round the small play button (now a plain ring), the frosted toast and drop overlay, and the blur in the change of screen. What stayed, each because it tells the listener something: the light behind the page (it is the music, it is black until a song plays, and `glow effect` turns it down to nothing), the gradient along a slider (where along it you are), the soft edge on reverb, the sheen on the speed slider (how fast the song is going) and the light along the import bar (that it is alive).

  - `vapor`: cyan, violet, hot pink. The three turn slowly round the middle of the page, and the ring opens out with the music.
  - `sunset`: violet, pink, orange. Sky across the top, pink along the foot of the page, an orange sun low in the middle.
  - `ember`: red, orange, amber. Three fires along the foot of the page, the top left dark.
  - `aurora`: green, ice blue, violet. Three tall curtains hung from the top, leaning one way and then the other.
  - `ocean`: aqua, sky, indigo. Four waves coming in from either side and going out past each other.
  - `forest`: lime, green, teal. Four smaller patches scattered over the page, each wandering round its own spot.
  - `rose`: pink, blush, peach. One bloom behind the player with two smaller ones moving inside it.

- `light` is paper with dark text. On it every glow's colours are a little deeper so they hold on white (`--c1` to `--c3` in the glow's `[data-theme="light"][data-glow="..."]` block), while the light behind the page (`--a1` to `--a3`, the bright three as numbers) is left as bright as on `dark` and tints the paper. That is the one place a look uses colours that are not its `--c1` to `--c3`. Umair asked for the bright colours there on 2026-11-14; before that the glow on `light` was dark ink.
- A glow has to look as good on paper as on black. Colour on paper is only a tint where on black it is a light, so it takes more of it to show as much: `--aura` is 0.88 on `light` against 0.78 on `dark` (it was 0.62 until Umair found `rose`, by then the default, drowned out on `light` next to the same glow on `dark`, 2026-11-14). `rose` goes further, because blush and peach are nearly the colour of paper themselves: on `light` its three lights are its own colours made hotter (`--a1` to `--a3` in its light block) at all of their strength (`--aura: 1`). Any new glow in pale colours will need the same, so look at it on both themes side by side before calling it done.
- Every colour in `src/styles.css` is a variable in the block at the top of that file and nothing below it names a colour, so keep it that way. The block is in a fixed order, and the order matters because the later of two equal rules wins: `dark` with `classic`, then each glow on a dark page, then `light`, then each glow on a light page. To add a glow: its two blocks there (colours, the speed slider's opposite three, `--on` for words on its colour, `--aura` if it is bright enough to need less, and `--mini`, a small still of it for its tile on `themes`), its shape under "light behind everything" in the same file, and its name in `GLOWS`. Words on a glow's colour are white on `classic` and dark on all the others, which are brighter somewhere along them; check any new one for that.
- How the glow is drawn (`.aura` in `src/styles.css`, reworked 2026-11-14 when Umair asked for it to be cooler and more prominent, D18). `Aura` in `src/ui.tsx` puts four empty elements behind the page. Each is one soft light whose place, size, colour and motion come from the glow as variables (`--x`, `--y`, `--w`, `--h`, `--a`, `--move`), measured in hundredths of the screen so a glow is one picture stretched to any screen. A light fades from its middle like a real one, with no hot centre and no edge (the stops in `.aura i`). At its loudest a light reaches `--aura` (0.78 on `dark`, less on the brightest glows there so white words stay readable, and 0.88 on `light`, where the words are dark and every glow can have the same; it was 0.42 and 0.3), and the lights also grow with the music (`scale`, from 0.8 to 1.14), so a loud part reaches further across the page than a quiet one. With no sound there is still nothing at all, the page is pitch black until the music lifts it.
- Grey words (`--mute`) are the colour of the page's words let through part way, not a grey of their own, since 2026-11-14. On the bare page that comes to the same grey as before, and with a bright glow behind them they lift with it instead of sinking into it, which is what keeps `info` and `themes` on the bottom line readable over `ember` and `sunset`. Keep the brightest part of any new glow away from the middle of the bottom line all the same, the small `sloverb` there is drawn in the glow's own colours.
- Words on a slider or on save are drawn twice in the same place, once over the bare part (`--over`) and once inside the fill, which is cut off where the fill ends: `--on` inside a slider's colour, `--ink` inside save, whose fill is the colour of the page's words (17:1 or more on both themes). That is what lets them read on a light page and on the brighter glows. Keep both copies if you touch `Slider` or the save button. Both copies are 19px bold since 2026-11-26, large text, because on some glows the words inside the colour only reach about 3.1:1 and large text needs 3:1 where smaller words need 4.5 (D25). Don't make them smaller or lighter without measuring every glow on both themes.
- The glow in the background follows the music and dances to it (`Aura` in `src/ui.tsx`, the sums in `src/core/dance.ts`). Two things happen at once:
  - The swell. How bright everything lit is follows how loud the song is, bent for contrast so quiet parts go nearly dark and loud parts glow, and eased over about two thirds of a second each way. That is `--level`, handed to everything with the class `hears`.
  - The dance, added 2026-11-14 when Umair said the glow had to react and dance to the music (D19). The engine also measures how much of the song is low (35 to 150Hz, the kick and bass), in the middle (300Hz to 2kHz) and high (4 to 12kHz, hats and snares) (`engine.hear()`). When one of those lands, a number eases up towards 1 over about a tenth of a second and back over nearly half of one: `--kick`, `--mid` and `--high`, set on the glow alone.
  - `--kick` is the beat, and every light moves on it together, which is what makes the page pump in time: each swells (`--pump`) and goes half its jump. Each light also has a part of its own (`--hit`: the first the low end again, the second the middle, the third the highs), on which it swells (`--swell`) and goes the other half. The jump (`--jx`, `--jy`) is in keeping with the glow: `ember`'s fires leap, `aurora`'s curtains drop, `ocean`'s waves surge in, `vapor`'s ring opens, `sunset`'s sun bounces.
  - How a beat is found, reworked the same day when Umair tried the first version on the live site and said it could be more on-beat. A hit is how fast a part of the music is rising, not how loud it is (`dance` in `src/core/dance.ts`), which is what a kick is, whatever bass is already sounding under it. Three things keep it to the real beats. A rise only counts above where that part has been sitting for the last fifth of a second (`usual`), because a loud master ducks its bass under every snare and hat and the way back up was being taken for a beat. Each rise is measured against the biggest lately (`big`), so the notes between the beats are let go and a dense, loud mix dances as hard as a sparse one, slowed and drowned in reverb or not. The beat is found in the frame it arrives, but what is drawn eases towards it (see the next point). Don't go back to "louder than usual", that was the first version: it trailed the beat and every light did something different.
  - The light waits for the sound. What the engine plays is heard a moment later, about 40ms on a laptop and a fifth of a second on wireless headphones, so `Aura` keeps what was heard (`Echo` in `src/core/dance.ts`) and dances to what is reaching the ear now, using what the browser says the delay is (`engine.lag()`, from `outputLatency` and `baseLatency`). Where a browser doesn't say, nothing is waited for. Measured on 2026-11-14 on made-up songs: the hit landed 30 to 50ms after each beat was played, against 42ms reported for the speaker.
  - It must never flicker, flash or jerk, and this is a safety rule, not taste. On 2026-11-14 a version went live that moved every light in a single frame on every kick and hat and lifted the brightness with each one, and Umair's words after trying it were that it was giving epilepsy. Flashing more than three times a second can set off a seizure in someone with photosensitive epilepsy. It was calmed within the hour, and these four things are what keep it calm, in `src/core/dance.ts` and `.aura i` in `src/styles.css`. Don't loosen any of them without Umair asking:
    - A hit never changes how bright the page is. Brightness follows only the slow swell.
    - Nothing moves in one frame. A light eases to a hit over about a tenth of a second (`EASE`) and settles over nearly half a second (`SETTLE`).
    - No part hits more than about three times a second (`APART`), however fast the song or its hats.
    - The moves are small: a light swells by about a twentieth and goes a third of its jump on the beat.
    The tests under `dance` in `src/core/core.test.ts` hold the first three. Measured after the change on a made-up 150 beats a minute song with ten hats a second: at most 2.4 hits a second in any part, brightness changing by under 1% a frame, size by under 2%.
  - Anyone who has asked their device for less motion gets the swell without the dance, and the lights stop drifting too.
  - How much of all this anyone sees is theirs to set with the `glow effect` slider on `themes`, from all of it down to `off` (`amount` in the look). It scales the swell and the hits alike, so at `off` nothing on the page moves with the music, while the glows that are there when it is quiet stay. Since 2026-11-26 `off` also holds them still, their drift paused where it is (`data-still` on `<html>`), so there is a way to stop the one thing that moves on its own without a device setting, as WCAG 2.2.2 asks (D25).
- The player rests when the page behind it is dark. Umair found on 2026-11-12 that with nothing playing and the background black, the colours and buttons at full strength were harsh on the eye, while with the glow up they looked right. So a veil of the page's own colour (`.rest` in `src/styles.css`, the last thing in `Player`) lies over the player at up to 30% (`--rest`) and thins as the light comes up, which makes the whole player softer when paused, in quiet parts or with the glow turned `off`, and full strength with the music. It is one layer whose opacity follows `--level`, so it costs nothing per frame. `light` sets `--rest` to 0, paper is never dark. If he wants it softer or stronger, `--rest` is the one number to change.
- The one exception to a glow's three colours is the speed slider, which Umair asked on 2026-11-12 to stand out wildly from everything else while still fitting. It has its own three (`--s1` to `--s3`, used by `.slide--speed` in `src/styles.css`), each roughly the opposite of the page's own: gold, lime and mint (`#ffc04d`, `#d9ff5c`, `#5cffc0`) on `classic`, and likewise opposite on every other glow except `mono`, where it is white on `dark` and ink on `light`. On `light` they are deeper, like the page's own. A gradient left to right with a glow that breathes with the music. Nowhere else.
- No emoji. No sharp rectangles.
- Nothing decorative. If it doesn't help someone make their song, it goes.

Top to bottom, the rule is that the room above whatever is on screen equals the room between it and the bottom line, at every size (D17, as amended the same day). `.screen` is a column of flexible parts: empty room, the thing on screen, and a foot with the bottom line at the bottom of it. Don't use a grid for this: with only a least height a grid sizes its rooms to the bigger one and overflows a short screen. When the screen is too short, the thing never comes closer to the bottom line than `--gap` (a margin on `.bar`). `.bar` has a fixed height of 48px so the foot is always worked out from the same number.
- Nothing that comes and goes may change the height of a centred screen, or all of it jumps. `reset` hangs under the sliders (and `cancel` in its place while a save is being made), and `cancel` and an import's error hang under the link box, all positioned so they take no room. The toast (`added`, `can't read that file`) appears on the bottom line, over the words there, because any place above it covers `save` on a short screen.
- `scripts/layout-audit.js` measures all of this. With the dev server running, `await import("/scripts/layout-audit.js")` in the browser console, then `await audit.player()`, `audit.summary()` and `await audit.others()` print where everything is and how far it is from the middle. Run it after touching the layout, at 320x568, 360x640, 375x553, 390x664, 390x844, 768x1024, 1440x900, at 967x507, which is the laptop window Umair looks at it in and was missed until 2026-11-14, and on its side at 640x360, 667x375 and 844x390. `room above` should equal `room down to the bottom line`, `centred on` should be the same number for the start screen, the player, `info` and `themes` at one size, every `off` should be 0, and the page should never be bigger than the screen. Add a laptop window, 1440x790, to that list: it is where an imbalance shows most.

To its left is a small play and pause (`MiniPlay` in `src/ui.tsx`, added 2026-11-12 at Umair's request), so the music can be stopped from the start screen: the player's button in miniature, the same glyph inside a thin plain ring, with no filled disc because that line is meant to be quiet. The line is held to the column (`max-width` on `.bar`, which lets what is drawn on a full line run to the column's edges, the room for a finger inside the first and last thing on it going past them), so a long song name never pushes `themes` off the edge. **Controls**
- As few as possible. Two sliders, `reset`, the transport and save, and `cancel` in `reset`'s place while a save is being made (added 2026-11-27 at Umair's request, like the import's `cancel`; under save there is too little room on a short screen, 28px at 967x507, D31). Cancelling says nothing went wrong and downloads nothing: the MP3 thread is ended there and then, and the offline render, which can't be stopped, runs on unseen and is let go (`cancelSave` in `src/audio/engine.ts`, the `signal` in `src/audio/save.ts`). Until 2026-11-12 there was no page of options at all; Umair then asked for one (D15, called `settings` until he renamed it `themes` on 2026-11-14), for how sloverb looks and nothing else: the `glow effect` slider, the glows and the two themes. Nothing about the sound belongs there, and it is not a place to park options. Anything added to it should be something a listener would actually want to change about the look.
- The sliders are the only way to change the sound. There were three presets (`slowed`, `original`, `nightcore`), Umair had them removed on 2026-11-12 so that moving a slider is the whole experience. Every visit starts with the song as it was recorded, 1× and 0% reverb (`DEFAULTS` in `src/core/settings.ts`), and `reset` glides both back there and is only visible once one has moved. `reset` is 18px and takes a press anywhere across the middle half of the column, for the full height between the sliders and save: Umair found it small and fiddly on 2026-11-12, people want to reset quickly. Each song in the list keeps its own speed and reverb (`settings` on a `Track` in `src/audio/engine.ts`, D16): the sliders change the song that is playing and no other, a song that hasn't been touched starts as recorded, and going back to one finds it the way it was left. Until 2026-11-12 one pair of settings carried over from song to song. They are kept only for as long as the page is open, like the list itself.
- The speed slider has nothing written on it, no name, no number and no middle mark, on purpose: Umair wants it to feel mysterious, you find out what it does by moving it. It is the biggest control on the page. Its value is still given to screen readers through `aria-valuetext`. The reverb slider keeps its name and percentage.
- The sliders show what they do: the speed one has a sheen running at the song's speed while it plays (a Web Animation whose `playbackRate` is the speed, so no script runs per frame), the reverb one's edge goes soft with the amount. That feedback follows the sound, not the finger.
- A slider reaches 0 and 100% when the finger is still 26px in from its ends (`REACH` in `src/ui.tsx`), and the travel between is stretched to match. Umair found on his iPhone, in a case, that the ends were too close to the edge of the screen to get to (2026-11-12). The sliders look the same and are as wide as before; the colour's edge just runs slightly ahead of the finger towards the ends. The waveform is not treated this way, its playhead stays under the finger.
- Every touch on a slider belongs to the slider (`touch-action: none` on `.slide`), and a drag never depends on pointer capture working (`hold()` in `src/ui.tsx`, used by the sliders and the waveform): the slider remembers which pointer pressed it and follows that one, and capture is only tried as a help. On Umair's touch screen ThinkPad (2026-11-16) the sliders did nothing at all under a finger. The two likely causes, both removed: they had `touch-action: pan-y`, which hands any drag that starts a little upright to the browser to scroll a page that doesn't scroll, and they only followed a pointer the browser said was captured, so a refused capture threw and ignored the press. Umair confirmed the fix on the ThinkPad the same day. The waveform keeps `pan-y`.
- Nothing reacts to a press on a slider: no glow, no swelling grip, no light coming up behind the page. Those were tried and Umair removed them on 2026-11-12 as icky and bloated. Don't add press or hold effects to the sliders, or anything that lights up out of nowhere when touched.
- A song's name that is too long for its place slides through it instead of being cut short, in the player's heading and beside the bars at the bottom of the start screen (`Marquee` in `src/ui.tsx`, asked for by Umair on 2026-11-12). It measures whether the name fits, again whenever its place changes size, and only then draws the name twice and moves it with a CSS animation on `transform`: setting off half a second after it appears and then never resting (it rested for a fifth of each trip at first, which Umair found took too long to get going after changing screen), at a pace tied to the size of the letters, fading at both ends, and only while the song plays. A name that fits is left alone and stays centred. With reduced motion a long name gets an ellipsis instead. Use `Marquee` for any other single line that may not fit.
- Song names are cleaned once, in `titleFrom` in `src/core/format.ts`, for files and YouTube titles alike: spaces of every kind trimmed and collapsed, invisible characters removed (zero-width, direction marks, soft hyphens, controls), underscores to spaces, the extension and any real folder path dropped, dashes left hanging at either end removed, accents joined. A slash inside a name is kept, so `AC/DC` survives. Don't use lookbehind in that or any other regular expression, iPhones before iOS 16.4 fail to load the whole page on one.
- No floating bars or pills of extras. The only things at the bottom of the screen are the words `info` and `themes`, in the same grey type with a thin rule between them, and, with a song open, the way between the player and the start screen beside them (`.bar` in `src/App.tsx`). Three things is as many as fit a 360px phone, so nothing else goes on that line. There is no `add song` or `youtube link` in the player any more (removed 2026-11-12), adding happens on the start screen.
- The transport is the only place with icons: the song before, play or pause, the song after. The exceptions are the small plus beside `sloverb` at the bottom of the player and the small play and pause beside the playing song at the bottom of the start screen. Everything else is a word.
- Never make anyone configure anything to get their song. One save button, one format. `themes` is only for taste, and everything works without ever opening it.
